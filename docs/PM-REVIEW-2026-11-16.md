## 1. P0 — data can be lost or numbers become wrong

### 1. Event lines are not persisted
- **What:** `EventDetailPage` keeps the item list in React state built from a seed (`getEventSeedItems`). Add Item / cart,
  Modify, Delete, ownership, scan, broken reports, packages (Grouped) all live only in that state. Only a few side stores are
  persisted (stock cuts, closing checks, files, rentals, productions).
- **Why:** after a reload the added items, scans and broken reports are gone, while the stock ledger, checks and cuts remain —
  the event and the warehouse disagree. This is the biggest risk for the mobile app too.
- **Proposal:** one persisted line store per event (`emi_event_lines[eventKey]`, later `/events/{id}/items`), written by every
  action; seed only when nothing is stored. All other stores (checking, cuts) reference `lineId`.

### 2. Events are not persisted
- **What:** `EventPage` keeps events in state from `initialEvents`. New Event / Edit / Delete disappear on reload. Event Detail and
  reports read `initialEvents`, so a new event can't even be opened reliably (no seed items, not in reports or calendar).
- **Proposal:** persisted event store (`emi_events`) used by Event list, Event Detail, Calendar, Report, transfer picker.

### 3. Broken units stay in stock when stock was not cut
- **What:** "Continue anyway" on broken items reduces the line qty (`brokenWrittenOff`). Only when the line was **cut** does the
  loss reach the warehouse (the return gives back less). If no Cutting Stock stage was passed, the broken pieces stay in
  Warehouse Inventory and in asset value.
- **Proposal:** write-off creates a stock movement `Broken write-off` (−qty) on the line's row when the line was not cut; show
  broken totals in Stock History and the Event Report.

### 4. Deleting an event has no guard
- **What:** `confirmDelete` just removes the event. Cut stock stays deducted (reserved for an event that no longer exists),
  rentals stay Rented, productions keep pointing to it.
- **Proposal:** block delete when the event has cut stock, active rentals/outsource or productions not Done ("Return / cancel
  first"), like the vendor delete guard; otherwise allow and archive its records.

## 2. P1 — real-world flows without a path

### 5. No ending for items that never come back
- **Partial Return** has only "Return remaining". If items are lost or damaged beyond repair, the event can never be completed.
- **Proposal:** in the return popup, per line "Mark as lost / damaged" with qty + reason → stock movement `Lost` (for cut lines
  the reservation is closed without returning), counts as resolved. Optional "expected back by" date on partial returns.

### 6. Booking check when adding items
- The picker limits qty to the warehouse stock *now*; it ignores other events booked on the same days and ignores stock that is
  only cut later. Clashes are only visible in Event Calendar.
- **Proposal:** in the picker show "Available for <event dates>: stock − booked by overlapping events" (data from
  `lib/eventClashes.js`), warn on shortage, and offer "Rent the rest" (opens Rent Item pre-filled).

### 7. Rented / outsourced lines at closing
- At Ready for Checking, rented / outsourced lines are checked like our own, but returning them to the vendor is a separate
  action in the Rented / Outsourced tab; nothing stops "Returned & Completed" while a rental is still "Rented".
- **Proposal:** the For Return popup gets a second section "Back to vendors" (Mark Returned per rental); the event can only become
  Returned & Completed when rentals are returned too (or show "Partial Return — vendor items outstanding").

### 8. Production for an event: stock and event line
- Mark Done puts the produced qty into the deploy warehouse **and** adds a line to the event. If the event is past its Cutting
  Stock stage the new line is not cut, so the same pieces are both "in the warehouse" and "at the event".
- **Proposal:** when the event is past the cut stage, cut the produced line immediately (reserved for the event); otherwise it is
  cut with the rest. Show "Produced for <event>" in Warehouse Inventory.

### 9. Roles and permissions
- Viewer is not read-only; Staff can open `/event-status` by URL; any user can approve-like actions (Start Checking, For Return,
  delete events).
- **Proposal:** permission matrix (Admin / Staff / Viewer) — e.g. Event Settings, delete event, For Return and opname approval:
  Admin; field work (scan, check, notes, broken): Staff; Viewer: read only. Guard routes and buttons.

### 10. Undo / reopen
- Going back a stage does not restore cut stock; a closed event (Returned & Completed / Transferred) can't be reopened; a wrong
  For Return or transfer can't be reversed.
- **Proposal:** Admin "Reopen event" (back to Ready for Checking, reversing the return movements) and "Undo last transfer" while
  the target event has not used the line.

### 11. QR / scanning
- QR Code menu is a placeholder; scanning is a simulated popup per line; QR Type (Individual / Group) changes nothing.
- **Proposal:** generate labels (per item line or per box according to QR Type), printable from Event Detail; scan by camera on
  mobile with "not on this event / already scanned / which line" handling (see `docs/MOBILE-QA-ANSWERS.md` B7–B10).

### 12. Postphone / Disable
- They are ordinary stages after Finished; nothing defines what a postponed or cancelled event does with its stock, rentals,
  dates.
- **Proposal:** make them event actions, not stages: **Postpone** (new dates, keep items, release cut stock until resumed) and
  **Cancel** (release stock, cancel requested rentals/productions, keep history).

### 13. Other lists not persisted
- Moving orders (only their stock movements persist), Users, registration, Area / Sub Area / Category / Unit / Warehouse edits.
- **Proposal:** persist with the same store pattern; moving orders get a document (number, from, to, lines, by, date) shown in
  Moving Order history.

## 3. P2 — friction and polish

### 14. Reminders
Overdue rentals, partial returns waiting, incomplete items, low stock, opname waiting approval, events starting this week with
missing items — today only visible inside each page (Inventory badge is the only menu badge).
**Proposal:** a notification bell + Dashboard "Needs attention" list with links.

### 15. Reports
Event Report has rentals but not outsource cost, transfers in/out, partial returns, broken/lost value; Overview has no cost per
event. **Proposal:** add these to Event Report and an "Event P&L lite" (rental + outsource + production cost vs item value used).

### 16. Join by name
Items are matched by name everywhere; renaming an item in Inventory leaves old names on events, rentals and productions.
**Proposal:** store `itemId` on lines/records (backend first), keep name only for display.

### 17. Event duplication / templates
Recurring event types (weddings, galas) re-enter the same item list each time. **Proposal:** "Duplicate event" (copy lines,
areas, rentals as Requested) and saved templates.

### 18. Smaller gaps
- Cart is page state: items left in the cart vanish on reload (the Next warning helps only while the page is open).
- Event files and item photos live in browser storage (size limit ~5 MB) — needs real upload before production use.
- Stock opname: only one pending opname for the whole company; no draft / "save and continue later"; no scan to find a row.
- Rent / outsource: no cost approval, no invoice / payment status, no extension of the return date.
- Transfer target must be "upcoming + on-going"; no transfer to a warehouse other than the original.
- Allow Add Item = False also hides Rent / Outsource / Production — confirm with owner that this is wanted.
- Global search does not cover outsource records and event files.
