## 2. Inventory — Item Value and asset value (R28)

**Goal:** know what the inventory is worth.

- **Data:** every catalog item has `itemValue`: integer Rupiah **per unit**. Seed in `src/data/inventory.js`; since R31 the
  catalog is a persisted store (`lib/catalogStore.js`) and Item Value is edited in the item form (§11.1).
- **Inventory listing (`/inventory`):**
  - Columns **Item Value** and **Total Value** (`itemValue × totalStock`). Both are sortable.
  - A **Total Asset Value** card: Σ(itemValue × totalStock) over all items. When a filter is active, it
    also shows the filtered total. A `<tfoot>` row shows the filtered total too.
  - Items without `itemValue` show "Not set", count as 0, and the card says how many there are.
  - [ASSUMPTION] "total nilai asset … dibaca dari sum item value" = Σ(value × stock), not Σ(value).
- **Category filter is multi-select** (checkboxes, count per category, Clear). Empty = all categories.
  It's built with the `multiple` prop of `src/components/SearchableSelect.jsx` (value = array).
  [ASSUMPTION] Multi-select is for the filter only. An item still has exactly one `category`.
- **Inventory Detail (`/inventory-detail?id=`)** reads the shared catalog (`getCatalog()`). It shows
  Item Value, Total Value and a **Production History** table for the item.
- Warehouse Inventory rows have `valuation` = the same unit value, and `totalValuation = valuation × itemStock`.
  Since R31, saving a new Item Value copies it to every row of that item (§11.1).

**Acceptance (after R31):** with no filter and fresh storage, the card shows **Rp1.366.865.000**. It is computed from the
warehouse rows now, not from the old static `totalStock`, so it differs slightly from the R28 figure of Rp1.367.910.000.
Selecting Floral + Lighting still shows 26 items.

## 7. Event Report — rewritten (R30)

- **Route:** `/event-summary?name=<event key>` (a plain upper-case name is also accepted). Sidebar:
  Report → **Event Report**. Linked from the Event list "Summary" icon and the Event Detail summary modal.
  With no `?name=`, the event with the most items opens.
- **Design goal:** stay fast and readable with **hundreds of item lines** (tested with 312 lines: about 0.5 s to load,
  about 0.5 s to render all rows).
- **Sections:**
  1. Header: event picker (all events), **Export CSV** (filtered rows), **Print**.
  2. Event strip: name, code, dates, location, "Stage x/y: name" or "Event finished", status badge, Open Event Detail.
  3. KPIs: Item lines (+ total pcs), Value in use (short Rp, full value in the sub line), Checked %, Scanned in %,
     Scanned out %, Broken (lines + pcs).
  4. **Progress by Area** table: sortable (area, lines, qty, value, checked %, scan in %, scan out %, broken),
     inline bars. Clicking a row toggles that area in the item filter.
  5. Breakdown cards: Progress, Ownership, Category, Added at stage.
  6. **Items** table:
     - Toolbar: search (deferred), area multi-select, progress, owner, category, Clear filters, Group by area (on by default).
     - Sortable columns. Sticky header in a scroll box (max 70vh). Group header rows with subtotals.
     - Rows per page 25 / **50** / 100 / All. First/prev/next/last.
- **Progress of an item** (one value, first match wins): Broken (`brokenQty > 0`) → Scanned out (`scanOut`) →
  Scanned in (`scanIn` or `scanned`) → Checked (`checking`) → Not checked. A ✓ marks cross-checked (`checked`).
- **Value** = qty × catalog `itemValue` (0 when the item is not in the catalog).
- **Print** renders all filtered rows (not just the page) with print CSS that hides the header/sidebar/toolbars.
- **CSV columns:** No, Item, SKU, Category, Area, Sub Area, Qty, Unit, Unit Value, Total Value, Ownership, Added at stage,
  Progress, Checking, Scan In, Scan Out, Cross-checked, Broken qty, PIC, Note.
- **Performance rules:** enrich items once (`useMemo`), compute all aggregates in one loop, render only the current
  page, `useDeferredValue` for search. Don't add per-row lookups inside render.

## 12. R32 — Event Calendar with item clashes, Event Report v2, Stock Opname Report

Owner request (verbatim): *"1. Kalender event yang menampilkan bentrok pemakaian barang: barang yang sama dipesan dua event di
tanggal yang sama. 2. Report event tolong dibuat lebih baik lagi 3. Report stock opname tolong dibuat jika belum ada"*

### 12.1 Event Calendar (`/event-calendar`, sidebar Events → Event Calendar)
- **Booking window** of an event = earliest of `date` / `start` → latest of `finish` / `start` / `date` (inclusive). The `date`
  field is the load-in / preparation date, so items are blocked from then on.
- **Demand** of an event = Σ qty per item name over its items (`getEventSeedItems`). Excluded: lines with `ownership: 'Outsource'`
  or `fromLoan` (not our stock), names not in the catalog, events with `itemCount` 0, and Transferred events.
- **Clash** = on a given day, the same item is in the demand of ≥ 2 events whose windows include that day.
  - **Shortage** when the combined qty > total stock (Σ warehouse rows).
  - **Shared** otherwise.
- **UI:**
  - Monday-first month grid: event chips per day (max 3 + "+n"), a clash badge, and a red tint for shortage days / amber for shared.
  - Month nav, Today, a "Shortages only" toggle, and KPIs (events, clash days, items clashing, items short).
  - Clicking a day opens a side panel with that day's events and its clashes (needed vs in stock bar).
  - Below the grid: the month's clashes merged into date ranges, shortages first.
- Code: `src/lib/eventClashes.js`: `bookingWindow`, `eventsInRange`, `computeClashes(from, to)` → `{ byDay, list, events }`,
  and `clashesForEvent(key)`. The per-event demand is cached for the session.
- Demo data: 2 new events overlap big ones on purpose:
  - **Corporate Gala Bali** (id 100, 12–14 Jul) clashes with Wedding Bali Season.
  - **Summit Afterparty** (id 101, 30 May–1 Jun) clashes with Corporate Summit 2026.
  - Past clashes exist in March–April 2026.
- Generated event lines now take 8–33% of the item's real stock (capped by the category range), so overlaps produce
  both shared and short items.

### 12.3 Stock Opname Report (`/stock-opname-report`, sidebar Report → Stock Opname Report)
- Source: `getOpnameHistory()`. Definitions:
  - counted lines = `countedCount` (rows counted in that warehouse; older records fall back to the changed rows).
  - lines off = items with `diff ≠ 0`.
  - accuracy = 1 − off / counted.
  - shrinkage = Σ value of negative diffs; found extra = Σ value of positive diffs.
  - unit value = the line's `valuation`, else today's catalog Item Value.
- Filters: warehouses (multi), status (**Approved by default**, because rejected and pending opnames never changed stock),
  date range, item / counter search.
- **Sections:**
  - KPIs: opnames, accuracy, net difference, shrinkage, found extra, Poor lines.
  - By Warehouse: least accurate first, with "days since last approved opname". A warehouse is flagged **Due** after 60 days.
  - Monthly trend: accuracy and shrinkage bar.
  - Items most often off: by value lost, top 15.
  - Opname log: click a row to see its lines and the reject reason.
- Export CSV (line level) and Print (expands every opname).
- `StockOpnamePage` now saves `countedCount` and each line's `valuation` on submit. Seed: 14 opnames (12 approved, 2 rejected)
  over Nov 2025–Apr 2026, across all 5 warehouses (`data/stockOpnameHistory.js`).
